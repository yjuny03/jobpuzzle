## 1. 맞춤 분석 8번 연속 실패

### 문제
맞춤 종합 분석(JSON-05)은 공고 분석·자료 분석·직무 가이드를 합쳐 최종 결과를 만드는 단계입니다. 실제 Claude를 붙이자 이 단계가 8번 연속 실패했습니다.
실패할 때마다 이유가 달랐고, 그 이유를 프롬프트 규칙으로 하나씩 막으면 다음 실행에서 또 다른 곳이 깨졌습니다.

| 실행 | 프롬프트 | 입력 토큰 | 출력 토큰 | 기록된 실패 |
|---:|---:|---:|---:|---|
| 1 | v1.1 | 81,211 | 13,280 | provider 경계 오류로 분류 |
| 2 | v1.1 | 80,092 | 96 | readiness.reason 누락 |
| 3 | v1.1 | 81,696 | 11,934 | provider 오류로 잘못 분류 |
| 4 | v1.2 | 44,108 | 12,959 | 실패 기록 중 RUNNING 상태로 남음 |
| 5 | v1.2 | 42,568 | 120 | 요구사항 일부 누락 |
| 6 | v1.2 | 미기록 | 미기록 | 지원하지 않는 schema로 HTTP 400 |
| 7 | v1.2 | 42,732 | 8,680 | 지원자 근거 위치(source identity) 오류 |
| 8 | v1.2 | 42,545 | 11,650 | 존재하지 않는 근거 ID |

출력이 만 토큰 넘게 정상으로 돌아온 실행도 서버에서 버려졌습니다. 실패 한 번마다 약 4만~8만 토큰이 그대로 비용이 됐습니다.

### 원인
에러 하나하나를 보면 "AI가 실수했다"로 보였지만, 코드를 처음부터 읽어 보니 **AI가 무엇을 돌려줘야 하는지에 대한 약속이 계층마다 달랐습니다.**

| 계층 | 요구하던 것 |
|---|---|
| 프롬프트 본문 | 근거를 `candidateSourceRefs`(문서·페이지·문장 위치)로 반환 |
| 프롬프트 렌더러 | 프롬프트 끝에 "위치 대신 `candidateEvidenceIds`로 반환" 지시를 덧붙임 |
| 응답 schema | `candidateEvidenceIds`만 허용 |
| 응답 DTO·검증 | 두 방식을 모두 받으면서 새 방식도 강제하지 못함 |

AI가 어느 지시를 따르든 다른 계층과 부딪힐 수 있는 구조였습니다.
게다가 문서 위치, 내부 ID, 요구사항 원문처럼 **서버가 이미 정확히 아는 값까지 AI에게 다시 쓰게** 하고, 한 글자라도 다르면 응답 전체를 버렸습니다.

진단 로그로 확인한 대표 사례가 있습니다. AI는 요구사항 ID를 맞게 골랐는데 요구사항 문구를 살짝 바꿔 썼고, 서버 검증이 이를 원문과 글자 단위로 비교해 실패시켰습니다(5번 항목 참고).

### 해결
검증을 느슨하게 만들지 않고, **AI가 고를 것과 서버가 만들 것을 다시 나눴습니다.**

| AI가 하는 일 | 서버가 하는 일 |
|---|---|
| 요구사항별 충족 수준 판단, 판단 이유 | 요구사항 ID·유형·원문 (공고 분석 결과에서 복원) |
| 허용된 근거 ID 중에서 고르기 | 근거의 문서·페이지·문장 위치와 원문 |
| 질문 문구, 질문 의도, 개선 제안 | match·질문·개선 과제의 내부 ID와 서로의 연결 |

- AI에게는 서버가 만든 **짧은 ID 목록**만 주고, 그 안에서 고르게 했습니다.
- ID가 목록에 없거나, 중복되거나, 요구사항이 빠지면 지금도 **실패로 처리**합니다. 엄격함은 그대로 두고 대상만 바꿨습니다.
- 계층마다 달랐던 약속을 한 문서(`JSON05_v1.3_Provider_계약명세`)로 모으고, schema·렌더러·검증을 그 문서에 맞췄습니다.
- 이 방향을 v1.3에서 정한 뒤에도 한 번에 끝나지 않았습니다. 응답 구조를 v1.10까지 여러 차례 다듬은 끝에 맞춤 분석이 성공했습니다.

### 결과
- v1.10으로 실제 Claude 전체 분석(공고 → 자료 → 맞춤 분석)이 완료됐습니다(2026-07-28, case 20). 당시 인수인계 문서에 맞춤 분석 성공이 "미완료"로 남아 있던 뒤의 첫 완료 기록입니다.
- 이 전체 분석의 AI 호출 18회(공고 1회, 자료 조각 16회, 맞춤 분석 1회)와 집계 1회가 **모두 성공, 재시도 0회**. 전체 **5분 53초**.
- 맞춤 분석 입력은 21,118 토큰이었습니다. 실패하던 실행과 입력 자료가 달라 같은 조건의 비교는 아닙니다.

### 성공한 뒤에 확인한 것
성공한 결과를 열어 보니 저장된 질문 6개 중 1개가 `placeholder?`였습니다. 나머지 5개는 AI 질문이 부족해 서버가 채운 것이었습니다.
검증이 "비어 있지 않고 물음표로 끝나는지"만 보고 있었기 때문입니다. 같은 날 의미 없는 질문 문구를 거르는 검사를 추가했습니다.
**"COMPLETED"가 곧 "제대로 된 결과"는 아니어서, 상태뿐 아니라 저장된 결과도 확인해야 한다**는 것을 배웠습니다.

## 2. 같은 근거가 반복 전달돼 입력이 두 배로 커짐

### 문제
맞춤 분석 입력이 한 번에 약 8만 토큰이었습니다(위 표 1~3번). 실패가 잦은 상황이라 한 번 실패할 때의 비용이 컸습니다.

### 원인
맞춤 분석은 요구사항마다 지원자 자료에서 관련 근거를 검색해(RAG) 함께 보냅니다. 그런데 한 근거가 여러 요구사항에 동시에 검색되는 일이 많았고, 프롬프트에는 **요구사항마다 근거 원문을 통째로** 넣고 있었습니다.

| 기록된 실행(8번)의 검색 결과 기준 | 값 |
|---|---:|
| 요구사항별 근거 참조 수 (전체 합) | 33개 |
| 실제로 서로 다른 근거 | 8개 |
| 참조 기준 원문 합계 | 46,276자 |
| 중복을 뺀 원문 합계 | 9,872자 |

근거 하나가 평균 4번 정도 여러 요구사항에 함께 검색됐습니다. 원문을 요구사항마다 넣는 방식이었다면 같은 원문이 그만큼 반복됩니다. 이 숫자는 중복 제거 이후 실행(v1.2)의 검색 기록에서 센 값이고, 중복 제거 전 프롬프트를 직접 잰 값은 아닙니다.

### 해결
서로 다른 근거만 한 번씩 **근거 목록**으로 넣고, 요구사항에는 그 근거의 ID만 연결했습니다. 이 근거 ID 목록이 1번에서 AI가 고르는 "허용된 근거 ID"입니다.

### 결과
맞춤 분석 입력 토큰이 **약 8만(80,092~81,696) → 약 4.3만(42,545~44,108)**, 약 46~48% 줄었습니다(위 표 v1.1 → v1.2). 당시 구조 점검 문서는 이 감소를 중복 제거의 효과로 기록했습니다. 다만 두 버전의 실행이 같은 입력이었는지는 기록에 없어, 같은 조건의 비교라고 단정하지는 않습니다.

### 입력 크기 검사
당시 구조 점검에서는 "AI 호출 전 입력 크기 검사가 중복을 포함한 합계로 계산돼, 실제로는 작은 입력도 거부될 수 있다"는 문제도 함께 지적됐습니다.
이후 응답 형식을 1번처럼 바꾸면서 현재 사용하는 맞춤 분석(v1.10)은 **실제로 만들어진 프롬프트의 길이**로 검사합니다. 중복 합계 검사는 이전 버전(v1.1·v1.2) 경로에만 남아 있어, 지금 분석에는 영향이 없습니다.

## 3. 긴 지원 자료 응답이 도중에 잘림

### 문제
이력서·자기소개서를 한 요청으로 보내면 Claude 응답이 출력 상한에 걸리거나 JSON이 중간에 끊겼습니다.

### 원인
- 자료 전체가 한 요청에 들어가, 돌려받아야 할 JSON 자체가 길었습니다.
- AI의 사고 과정(thinking)과 JSON 출력이 **같은 출력 예산**을 나눠 쓰고 있었습니다.

### 해결
- 자료에서 사실을 뽑아내는 단계라 깊은 추론이 필요하지 않다고 보고, 이 단계의 thinking을 껐습니다.
- 자료를 근거 표시(marker) 경계에서 나눴습니다. 기준은 실제 AI 연동 프로필(`ai-e2e`) 기준 한 묶음에 최대 2개, 4,500자입니다(기본 설정은 8개, 12,000자). 묶음마다 따로 호출하고 서버에서 합칩니다.
- 합친 뒤에는 모든 근거 위치가 전체 자료 안에 있는지 **다시 한 번 검증**합니다. 묶음마다 통과해도 합친 결과가 맞는지는 따로 확인해야 하기 때문입니다.
- 묶음마다 입력 지문(fingerprint)을 남겨, 같은 입력의 성공한 묶음은 다시 호출하지 않습니다.

### 결과
근거 표시 7개를 2·2·2·1개씩 4번 나눠 모두 성공했고, 지원자 자료 분석 결과까지 만들어졌습니다.
이 분할 구조는 이후 [자료 분석 병렬화](measurement-driven-improvements.md)의 바탕이 됐습니다. 나뉜 호출을 순서대로 하나씩 실행하던 것을 동시에 실행하도록 바꿨습니다.

## 4. 보내지 않은 문서를 AI가 지어냄

### 문제
3번에서 자료를 문서별로 나눠 보내자, 이력서만 담은 요청에 AI가 **자기소개서 결과까지 만들어** 돌려줬습니다. 서버 검증에서 거부됐습니다.

### 원인
"보내지 않은 문서는 null로 두라"는 지시가 프롬프트 문장에만 있었습니다. 문장은 AI가 따를 수도, 안 따를 수도 있습니다.

### 해결
Anthropic의 구조화된 출력(Structured Outputs)을 사용해, **요청에 담긴 문서 유형에 맞춰 응답 schema를 매번 만들었습니다.**
- 이력서 묶음이면 이력서 칸만 객체를 허용하고, 나머지 문서 칸은 null만 허용합니다.
- 이 응답에 포함된 문서 유형 목록도 해당 유형만 허용합니다.
- 근거는 위치 ID만 AI가 고르고, 근거 원문은 서버가 원래 자료에서 다시 채웁니다.

### 결과
"지키라고 말하는 것"에서 "형식상 다르게 쓸 수 없는 것"으로 바꿨습니다. 이 schema를 적용한 상태로 3번의 분할 실행이 모두 성공했습니다.

## 5. 실패 원인이 "AI 오류" 한 가지로만 남음

### 문제
Claude 응답은 정상(end_turn, 사용량 기록까지 정상)인데 서버에는 **502와 `PROVIDER_ERROR`만** 남는 실패가 있었습니다. 1번 표에도 "provider 오류로 잘못 분류"된 실행이 남아 있습니다.
AI가 실패한 것인지, 서버가 응답을 처리하다 실패한 것인지 구분할 수 없었습니다.

### 원인
AI 호출부터 결과 저장까지의 예외를 한 곳에서 잡아 모두 같은 오류로 바꾸고 있었습니다.

### 해결
- 맞춤 분석 실행 경로에 **단계별 진단 기록(checkpoint)** 을 남겼습니다. 개발 환경에서만 켜집니다.

  ```
  JSON05_TEXT_EXTRACTED → JSON05_PARSED → JSON05_PROVIDER_DTO_MAPPED
  → JSON05_SOURCE_REFS_RESTORED → JSON05_VALIDATED → JSON05_WRITTEN → JSON05_QUESTION_SET_CREATED
  ```

- 실패하면 마지막으로 통과한 checkpoint, 예외 종류, 근본 원인, 첫 번째 애플리케이션 코드 위치를 남깁니다. 프롬프트·응답 원문·API 키는 남기지 않습니다.
- 오류 유형을 제공자 오류 / 응답 파싱 오류 / 검증 오류 / 근거 위치 오류 / 출력 한도 오류로 나눠 기록했습니다.

### 결과
진단 로그에서 `JSON05_PROVIDER_DTO_MAPPED` 다음 검증(`validateMatches`)에서 요구사항 문구 불일치로 실패한 것을 찾았습니다. 이것이 1번의 대표 원인을 찾은 단서였습니다. 이 실패가 1번 표의 몇 번째 실행인지는 기록에 남아 있지 않습니다.
그 뒤로는 실패해도 같은 조건으로 AI를 다시 호출해 보지 않고, 진단 로그로 위치부터 좁혔습니다. 실제 AI 호출은 비용이 들기 때문입니다.

## 6. 벡터 DB 용량 초과 위험

### 문제
배포 환경의 벡터 DB인 Qdrant Cloud 무료 플랜은 메모리·디스크 자원에 한도가 있습니다. 한도를 넘으면 색인 실패로 끝나지 않고 **모든 사용자의 검색이 함께 느려지거나 멈출** 수 있었습니다.
또 같은 이력서를 여러 공고에 쓰면 매번 새 벡터가 쌓이는 구조여서, 로컬 DB에서도 같은 내용의 청크가 반복해 저장된 것을 확인했습니다.

### 설계 판단
| 질문 | 결정 | 이유 |
|---|---|---|
| 어디서 막을까 | 분석 실행(`/run`)이 아니라 **색인(`/index`) 단계** | 색인 전에 막아야 이미 쌓인 데이터와 분석 결과에 영향이 없음 |
| 현재 사용량은 어떻게 셀까 | `points/count`를 `exact: true`로 조회 | 한도를 "거의" 지키는 게 아니라 절대 넘기지 않는 게 목적이라 근사치를 쓰지 않음 |
| 조회가 실패하면 | 색인 차단 | 용량이 위험한 순간에 보호 장치가 꺼지면 안 됨 |
| 동시에 색인하면 | 개수 확인부터 저장까지 하나의 잠금 안에서 처리 | 두 요청이 같은 낮은 개수를 읽고 함께 통과하는 것을 막음 |

### 구현하며 바로잡은 것
- **저장 응답이 "저장 완료"를 뜻하지 않았습니다.** Qdrant는 `wait` 없이 저장하면 실제로 반영되기 전에 응답합니다. 잠금을 풀어도 다음 요청이 아직 반영되지 않은 낮은 개수를 읽을 수 있었습니다.
  - 로컬에서 직접 확인했습니다. `wait` 없이 저장하면 `acknowledged`(0.3ms), `wait=true`면 `completed`(13ms)가 돌아왔습니다.
  - 용량 검사를 켰을 때는 `wait=true`로 저장하도록 바꿨습니다.
- **처음 짠 잠금 해제 테스트는 버그가 있어도 통과했습니다.** `ReentrantLock`은 같은 스레드의 재진입을 허용합니다. 그래서 "실패 후 같은 스레드에서 다시 호출"하는 테스트는 잠금을 풀지 않는 버그가 있어도 성공합니다. 서로 다른 스레드로 검증하도록 바꾸고, 3회 반복해 결과가 흔들리지 않는 것을 확인했습니다.

### 결과
- 용량을 넘는 색인은 503(`VECTOR_CAPACITY_EXCEEDED`)으로 막고, 일반 Qdrant 장애(502)와 구분했습니다.
- RAG 단위 테스트 50개(신규 8개)가 통과했습니다. 실제 로컬 Qdrant와 OpenAI 임베딩으로 확인한 흐름은 "한도 초과 시 차단(벡터 증가 0건) → 한도 복원 후 재시도 성공"입니다.
- 검사를 끈 상태(기존 경로)로 실제 전체 분석이 정상 완료됐고, 벡터는 545→549개로 새 청크 4개만큼만 늘었습니다. 검사를 켠 상태의 실제 전체 분석은 기록이 없습니다.

### 한계
- 잠금은 서버 한 대를 전제로 합니다. 서버를 여러 대로 늘리면 DB 잠금이나 별도 카운터로 바꿔야 합니다(코드 주석에 남김).
- 한도 50,000개는 Qdrant가 정해 준 값이 아니라, 벡터 하나의 메모리 사용량을 추정해 역산한 값입니다. 실제 운영 메모리 사용량으로 다시 맞춰야 합니다.
- 같은 내용의 벡터가 쌓이는 문제 자체(중복 제거)는 이 작업 범위 밖이라 해결하지 않았고, 이 가드는 그 상황에 대비한 안전장치입니다.

## 7. 공통으로 남은 원칙

1. **AI는 고르고 판단하고, 서버는 이미 아는 값을 만든다.** ID·원문·위치를 AI에게 다시 쓰게 하면 그만큼 틀릴 곳이 늘어납니다.
2. **검증은 느슨하게 하지 않고 대상을 바꾼다.** AI가 고른 ID는 엄격하게 확인하고, 자유롭게 쓴 문장은 원문과 글자 단위로 비교하지 않습니다.
3. **프롬프트 문장보다 형식으로 강제한다.** 지켜야 하는 규칙은 schema로 표현합니다.
4. **실패는 위치와 종류로 남긴다.** 같은 조건으로 다시 호출하기 전에 로그로 원인을 좁힙니다.
5. **성공 상태만 보지 않는다.** 저장된 결과를 직접 열어 품질까지 확인합니다.
